I have started to think of application code as a reviewable receipt. I now have AI generate almost all of it. My attention goes first to the purpose of a system: what problem it should solve, which decisions matter, and how I will recognize a useful result. The implementation gives me something concrete to inspect.

When I used that phrase in a conversation, I clarified what I meant:

“The guarantee is not correctness, but legibility to humans.”

A receipt makes an operation inspectable. It provides a record that I can question, compare with my intentions, and investigate when something goes wrong. Calling code a receipt does not relieve me of responsibility for the system it describes.

Where the work goes

I have never regarded physically typing code as the central purpose of software engineering. I want to think about problems and devise solutions. For a familiar problem, I am happy to use an established convention; I would rather spend my attention on the part that actually needs thought.

“Let the computer do the work” seems a natural extension of that preference. But delegating construction leaves an interesting question: how much understanding did I previously acquire simply by being the person who built the thing?

Working through an implementation can expose an awkward dependency, an unexpected write, or a costly query. I worry about losing those incidental discoveries when I move directly from intention to a generated result. Reading the result may recover some of that understanding. It does not automatically recover all of it.

The behavior beside the requirement

The difficult case is software that visibly works. It does what I asked, its code looks plausible, and the ordinary path behaves as expected. It may still do something I never intended.

Consider a hypothetical payment workflow. A successful run can demonstrate that a payment was recorded. It leaves other questions open: what happens if the request is retried, whether a partial failure leaves inconsistent records, and whether a second side effect occurs elsewhere. A convincing demonstration answers the question it exercises.

That makes me interested in evidence with different failure modes: reading the implementation, examining state changes, trying interrupted or repeated operations, and checking outcomes independently. Each gives me a different view of the same system. Agreement between them is more useful than simply asking for the implementation to be described again.

A receipt worth keeping

I would like the record of a piece of work to preserve its intent, implementation, observations, and unresolved questions together. Future investigation should be able to distinguish what was requested, what was built, and what was actually checked.

There is a philosophical shift here. The intellectual work of engineering can live in deciding what should happen and establishing whether it does. As implementation becomes easier to delegate, I expect to spend more of my attention on the consequences—especially the ones absent from the original request.
